## How to read this file

Findings are labelled `F-<AREA>-<N>`. Each carries eight fields, and a finding is only
actionable if all eight hold up:

1. verdict · 2. `file:line` evidence · 3. current complexity or invalid states ·
4. proposed representation · 5. smallest credible scope · 6. regression risks ·
7. validation required · 8. confidence

Two sections were written by later passes and **override anything earlier in the file that
disagrees with them**:

- **`AUDIT-THE-AUDIT — pass 4`** is the final adjudication. It rejects three findings,
  demotes five, reverses one dependency chain, and corrects the finding count. Where a
  per-lane section still says something like "land it first", pass 4 wins.
- **`AUDIT-THE-AUDIT — pass 1`** is the coverage record. Its table is authoritative for
  which subsystems were reviewed and which were skipped.

Rejections and demotions are kept deliberately. Each one looked reasonable, and knowing why
a change was declined is worth as much later as knowing why one was recommended.

Two IDs were assigned after the fact: the `RB-GENERATOR` finding is **F-GEN-1** and the
`TOOL-BUILD` finding is **F-TOOL-1**.

### RB-DAEMON — 2 accepted. Coordinator-verified.

**F-DAEMON-1: collapse `@cache` + `@key_mutexes` + `prune` into one bucket per key. ACCEPTED, HIGH priority.**
1. Verdict: recommend
2. Evidence (all independently verified): server.rb:98-100 (`@cache`, `@key_mutexes`, `@cache_mutex`); :477-497 `cached(kind, path, *extra)` — key at :481, per-key mutex at :487, value stored at :494; :503-508 `prune`, the only place `@key_mutexes` shrinks (:506); :272 the SOLE call site (`grep -n 'cached('` returns exactly :272 and the :477 definition), so `kind` is always `:build`; :515-521 `mtime_of`; :209-210 `handle` swallows a raising build.
3. Current complexity / invalid state: three fields express one fact ("one cached build per (path, sourcemap), superseded when mtime changes"). The invariant "`@key_mutexes` keys mirror `@cache` keys" is unenforceable AND VIOLATED: :487 inserts the mutex before :494 stores the value, while `prune` selects only from `@cache.keys` (:505). A key whose build RAISED (syntax error under `--watch` — the common case, swallowed at :209) never reaches `@cache`, so its `Mutex` is unreachable by `prune` and lives for the daemon's life. Every re-save of a broken file leaks another. Secondary fragility: `@cache.delete(k) && @key_mutexes.delete(k)` (:506) short-circuits on a falsy cached value — safe today only because values are Hashes. Secondary: `prune` re-scans all keys per request and filters `k[0] == kind` on a constant.
4. Proposed: `@cache[[path, sourcemap]] = { mtime:, mutex:, value: }`. Replacing the bucket when `mtime` differs IS the prune, so `prune` and the `kind` parameter both go; the mutex lives in the bucket and dies with it — nothing to leak, no cross-map invariant. Keyed per variant, so the two sourcemap variants still build in parallel; no concurrency behaviour change.
5. Scope: server.rb only. Rewrite `cached` (~20 lines) as fetch-or-replace bucket under `@cache_mutex`, then `bucket[:mutex].synchronize` with a double-check on `bucket[:value]`. Delete `prune` (:503-508) and `@key_mutexes` (:99). Change :272 to `cached(path, sourcemap)`. Keep `return yield if mtime.nil?` (:479) verbatim — the `.rjs` no-cache guarantee rests on it. `handle`/`op_build` signatures unchanged.
6. Risks: (a) a build in flight against a replaced bucket writes into the orphan — harmless, but capture the bucket in a local and never re-read `@cache[key]` after the build; (b) identity caching must survive (`assert_same` on `[:code]`) — store the same Hash object, do not rebuild the reply; (c) never take `bucket[:mutex]` while holding `@cache_mutex`, that would serialise all builds.
7. Validation. Existing (verified present and sufficient): test/runtime/server_test.rb:165-215 — repeated build served from cache (`assert_same`), `.rjs` not cached (`refute_same`), source map keyed on its source, mtime invalidation. Additional: nothing asserts bounded growth. Add one test — build a file that fails, bump mtime, repeat 3x, assert one entry for that path via `instance_variable_get`. That test fails today.
8. Confidence: high

**F-DAEMON-2: replace the `settled` flag + three racing promises in `spawnDaemon` with one deadline loop.**

> **DEMOTED to LOW by pass 4** — see the adjudication section near the end of this file. `bootstrap.js:144-150` explicitly defends `settled` and records the bug it fixed, and the proposed deadline loop trades a hard `setTimeout` for a cooperative check.
1. Verdict: recommend
2. Evidence (verified): bootstrap.js:151 `let settled = false`; :152-162 poll loop guarded by `settled`, with its own `throw` for the abandoned case; :164-170 `exited` promise that exists only to reject; :172-184 `timedOut` promise plus the `timer` handle hoisted out through closure; :187 `Promise.race([listening, exited, timedOut])`; :196-199 `finally` setting `settled` and clearing `timer`.
3. Current complexity / invalid state: four concurrent representations of one question. `settled` is checked only at loop top, so after a lost race the loop can still be inside `await Daemon.connect` and succeed — returning a live client for a process `proc.kill()` (:193) has already killed, then discarded. Stale async state patched with a flag rather than represented.
4. Proposed: the loop already polls; give it the deadline and the death signal. `const deadline = Date.now() + timeoutMs; let exitCode; proc.exited.then(c => { exitCode = c }); while (Date.now() < deadline) { if (exitCode !== undefined) throw ...; try { return await Daemon.connect(socketPath) } catch { await Bun.sleep(50) } } throw ...`. One loop, one mutable variable; no flag, no timer, no `clearTimeout`, no unowned-client window. Both error messages (:165-169, :178-179) preserved verbatim; `proc.kill()` + `rmSync` (:193-194) stays in the same catch. Reads `exitCode` from a `.then` rather than `proc.exitCode`/`signalCode`, so it does not depend on unverifiable Bun Subprocess property semantics (bun-types is not vendored in this repo — confirmed) and a signal death sets it just the same.
5. Scope: bootstrap.js only, inside `spawnDaemon` (:151-199). `register` (:211-244) and the `{ proc, client, socketDir }` return shape untouched.
6. Risks, named: exit detection latency goes immediate -> <=50ms (irrelevant against a Rails boot). Timeout is checked at tick boundaries, so a hung `Daemon.connect` could overshoot by one attempt; `Bun.connect` to a nonexistent unix path fails immediately, so in practice that is the 50ms sleep. Keep `proc.exited` attached.
7. Validation: NO JS-side test covers this path (verified — `bootstrap`/`spawnDaemon` appear in test/ and fixtures/ only in server_test.rb, the generator template text, and the preload). The three failure shapes are proven by hand today. Additional: one `bun test` file calling `spawnDaemon` with (a) `timeoutMs: 50` and no daemon asserting the "did not accept a connection within" message; (b) a command exiting non-zero asserting the "exited with status" message; (c) happy path asserting `tmp/proscenium/d-*` removed on both failures. (b)/(c) need an injectable command — if that is more surgery than the fix, ship (a) only.
8. Confidence: medium

Any `innerHTML =` or template insertion produces whitespace text nodes, so this is ROUTINE, not exotic.
